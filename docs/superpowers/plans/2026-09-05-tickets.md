# Tickets: membership gating, reserved seats, ticket types, Stripe, the door

Date: 2026-09-05. Builds on the member register
(`2026-09-05-member-register.md`) and Phase 2's events.

Decisions with the user: payments through **Stripe** (Checkout online,
Tap to Pay via the Stripe Dashboard app at the door, both landing on the
same webhook); Kide stays available as an external link for events where
its audience matters. One ticket per Discord account per event; walk-ins
by name at the door. Free events keep the one-click signup.

## Data (migration 0011)

- `events.members_only` (signups and tickets need a linked, current
  member), `events.member_slots` (seats within `capacity` only members
  may take; non-members stop at `capacity - member_slots`).
- `ticket_types`: per event, name, `price_cents` (0 = free ticket),
  `member_price_cents` (NULL = same), `members_only`, `quantity` (NULL =
  unlimited within capacity), `sales_close_at`, `sort`, `active`.
- `tickets`: event, type, `discord_id` (NULL for walk-ins), holder name,
  unique `code` (the QR payload, 10 chars of base32 with a check digit),
  amount, `status` pending → paid → refunded / void, `source` online |
  door | comp, Stripe session and payment intent ids, paid / checked-in
  timestamps and who checked them in. One live ticket per account per
  event (partial unique index).
- `door_payments`: Tap to Pay payments from the Dashboard app (no
  metadata) waiting to be attached to a ticket at the door.

## Code

- `src/lib/db.ts`: `signupAccess` (members-only + reserved seats, used by
  `setSignup`, team create/join, and ticket purchase), ticket type CRUD,
  `createTicket`/`markTicketPaid` (paid ⇒ a 'yes' signup for linked
  holders, bypassing capacity since the seat was counted at purchase),
  `checkInTicket`, `refundTicket`, sales summary, door payments.
- `src/lib/stripe.ts`: Checkout Session creation (form-encoded REST, no
  SDK; API version pinned; ticket metadata copied onto the PaymentIntent;
  `integration_identifier` tag), webhook signature verification
  (HMAC-SHA256, 5-minute tolerance). Reviewed against Stripe's
  best-practices skill 2026-09-05: fulfilment gated on `payment_status`,
  async payment events handled, restricted key recommended, no
  `payment_method_types`, webhooks required not optional. Secrets `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`;
  off until set (buy buttons say so, free tickets still work).
- `src/lib/qr.ts`: SVG QR codes via `qrcode-generator`.
- Routes: `/events/[id]/buy` (POST), `/stripe/webhook` (POST),
  `/tickets` (mine), `/tickets/[code]`, `/events/[id]/door` (Board role or
  register access: list, search, scan with `jsqr`, check in, sell by QR,
  attach tap payments), `/events/[id]/pay/[type]` (public buy-by-QR page,
  name typed on Stripe's page), `/events/[id]/tickets.csv`, admin ticket
  type management on the event page, `members_only`/`member_slots` on the
  event forms.
- Content: `terms.md` (terms of sale and cancellation), privacy policy
  addendum (Stripe as processor), OPERATIONS section "Selling tickets".
